# VMTest Suite Audit (nixcfg)

This document is the durable audit artifact for plan 054 P1: a full inventory and analysis of the nixcfg check suite (the "VMTest suite" plus its eval/build/lint siblings). It classifies every check by backend, records what each check actually asserts and which modules it touches, maps feature/code coverage, and derives the gaps, redundancies, weak tests, and backend-fit problems that feed the P2/P3 refactor work. The suite exports 106 checks per Linux system (identical on `x86_64-linux` and `aarch64-linux`); one of them (`vm-dev-team-vm-smoketest`) is re-exported into nixcfg-work as the aarch64 post-image-build gate.

Audited: 2026-08-21

## Reproducing this audit

```bash
# nixcfg (this repo): 106 checks, mirrored across both Linux systems
nix eval '.#checks.x86_64-linux'  --apply builtins.attrNames    # => 106 checks
nix eval '.#checks.aarch64-linux' --apply builtins.attrNames    # => same 106 (mirrored)

# nixcfg-work (private consumer): re-exports exactly one nixcfg check on aarch64
cd /home/tim/src/nixcfg-work
nix eval '.#checks.x86_64-linux'  --apply builtins.attrNames    # => 0
nix eval '.#checks.aarch64-linux' --apply builtins.attrNames    # => 1 (vm-dev-team-vm-smoketest, re-exported from nixcfg)
```

Definition files:

- [`modules/flake-parts/tests.nix`](../modules/flake-parts/tests.nix) (1430 lines) - the eval-*, build-*, lint-*, cross-module-*, module-*-integration, skill-injection-*, opencode-*, ssh-*, files-*, validated-scripts, config-snapshot, flake-validation, regression, user-configured, tmux-picker-syntax checks.
- [`modules/flake-parts/vm-tests.nix`](../modules/flake-parts/vm-tests.nix) (2106 lines) - the 22 `vm-*` tests; helpers `mkVmTest` (QEMU nodes) and `mkContainerTest` (nspawn containers).

## Backend legend

Each check is classified into exactly one backend:

- **qemu-node** - `pkgs.testers.nixosTest` with `nodes.machine` (full QEMU VM boot; asserts runtime behavior).
- **nspawn-container** - `mkContainerTest` (systemd-nspawn, ~5-7x faster than QEMU, with service-unit fidelity caveats: `sshd.socket` not `sshd.service`; networking differs; boot/kernel/hardware semantics do not apply).
- **runCommand-eval** - `pkgs.runCommand` asserting on evaluated config attrs (no boot). The check forces module-tree evaluation by inheriting a config attribute into the derivation env, then optionally runs bash assertions on the evaluated values.
- **build-dryrun** - builds or dry-builds a derivation or image (no runtime assertion beyond "it builds").
- **build-pkg** - builds a package derivation (bare `self'.packages.<name>` reference).
- **lint** - static lint (deadnix / statix / formatting / ps1-encoding / version).

Two structural facts inform the analysis. First, `nspawn` cannot host boot/kernel/hardware semantics, and a full-host-in-container triggers a conflict cascade (`nixpkgs.hostPlatform` is read-only + a `systemd-resolved` assertion fires), so the `vm-*` tests compose MODULES/layers rather than literal host configs. Second, host runtime content is largely covered by layer tests (dev-team layer -> `vm-dev-team-stack`; `system-cli` -> `vm-system-type-cli`; `system-default` -> `vm-system-type-default`), which is why per-host smoke tests are mostly redundant - with one exception, `nuc-apt-repo`, whose service set (`aptly-repo` + `apt-cacher-ng`) is genuinely unique and untested.

## Backend-fit observations

These feed the P2/P3 refactor - checks whose backend is mismatched to what they claim to test.

- **`ssh-service-configured` and `vm-ssh-management` mismatch names vs backends in opposite directions.** `ssh-service-configured` is named like a service test but is pure `runCommand-eval` (never starts sshd) - if a real service assertion is wanted it belongs on `nspawn` (socket-activated `sshd.socket`) or QEMU (`sshd.service`); as-is it should be renamed to reflect that it is an option-value eval. Conversely `vm-ssh-management` pays full two-node QEMU cost but mocks the module and makes no real cross-host connection - most of its assertions are eval-grade self-checks that do not need a VM.
- **`vm-sops-deployment` pays QEMU cost to test upstream CLIs, not a module.** It boots a full VM but drives the sops/age CLIs by hand and never imports the dendritic module. The module path is already covered by `vm-sops-secrets`; the CLI-tooling portion does not need a boot and would fit a `runCommand`/`build` harness.
- **`vm-nspawn-smoke` is the one intentional backend split and validates the nspawn path.** It is a deliberate nspawn twin of the QEMU `vm-system-type-cli`; its unique finding (`sshd.socket` socket-activation instead of `sshd.service` inside a container) is exactly the fidelity caveat that determines which future checks can move to nspawn. Boot/kernel/hardware assertions must stay on QEMU.
- **The `*-dryrun` eval forcers are correctly NOT VMs.** `build-thinky-nixos-dryrun` and siblings force `toplevel`/`tarballBuilder`/`images` evaluation without building - appropriate as `runCommand-eval`. They are named `build-*` but never build; a rename to `eval-*-toplevel` would reduce confusion (the true build-then-assert pattern is `activate-hm-thinky-nixos`).
- **The `build-images-*-dryrun` attribute-presence checks could assert more without changing backend.** They already force the `images` attrset; asserting a minimal structural property of the image derivation (not just key presence) would deepen them while staying eval-tier.
- **Candidate services for a real backend (`aptly-repo`, `apt-cacher-ng`) need QEMU or nspawn, not eval.** These are stateful HTTP/service workloads (REST API, GPG, caching proxy). `apt-cacher-ng` is a plain systemd service that likely fits `nspawn` (fast); `aptly-repo`'s GPG keygen + API-polling `ensure-repos` may want full QEMU. Either way an eval check would not exercise the behavior that makes them risky.
- **`activate-hm-thinky-nixos` is the correct build-dryrun model to widen.** It is the only check that builds an activation script and asserts on the artifact (catching the claude-code jq_args shell-quoting bug class). Note it is SKIPPED under `nix flake check --no-build`; extending the same pattern to a second host would widen activation-generator coverage cheaply.
