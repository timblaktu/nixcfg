## Background & decision (self-contained)

Today the unattended runner `run-tasks-<account>` (generated by
`modules/programs/claude-code/_hm/task-automation.nix`) executes ONE plan task per iteration: each
iteration launches a fresh autonomous `claude -p ... --permission-mode bypassPermissions` that edits
files and commits by itself, then the bash loop advances the `TASK:` cursor. Mode A (`/next-task`) was
changed (branch `feat/cc-context-fixes`) to execute the whole **independent frontier** concurrently.
This plan brings Mode B to parity.

**Why not the naive approach.** Making the bash loop fire several `claude -p` in parallel in the SAME
worktree is unsafe: N leaderless autonomous processes each run `git commit` and each rewrite the same
plan file's `TASK:` markers -> `index.lock` races (a hard project rule forbids parallel git in one
worktree, worse on WSL2 9p) and the stop-on-failure + event-journal machinery (both per-single-task)
break.

**Chosen design = option (b): give the runner a brain.** Instead of the bash loop parallelising
`claude -p` spawns, each iteration launches ONE orchestrating `claude -p` given the *frontier* prompt
("here is the independent frontier - orchestrate it yourself, fan out sub-agents, commit each task").
That restores a single intelligent coordinator in one worktree - exactly what makes Mode A safe -
while still executing independent tasks concurrently. Consequences the tasks below implement:
- One launch clears a whole **layer** of independent tasks; the next launch picks up the newly
  unblocked layer. Fewer, fatter iterations.
- Stop-on-failure moves from per-task to **per-layer**: if any task in the layer hard-fails, the
  orchestrator stops, leaves that task `IN_PROGRESS`, emits a blocking-failure sentinel; the runner
  halts the whole run (default `--on-failure stop`).
- The event journal's per-task `sha_before->sha_after` attribution can no longer be derived from
  outside one invocation; per-task commit detail becomes the orchestrator's responsibility, and the
  runner journals per-layer.

Reference reading before starting: `task-automation.nix` (whole file), especially `nextTaskMd`
(lines ~10-88), `PROMPT` (~line 477), `run_task` (~987-1200), and the main loop (~1384-1545). Also the
"Unattended Burndown Contract" section of `claude-code-user-memory-template.md`.

### T3 - Per-layer stop-on-failure semantics `TASK:PENDING`
Depends on T2.
Define how the orchestrating invocation signals a layer-level blocking failure (e.g. emits
`BLOCKING_FAILURE` on its own line naming the failed task, leaves that task `IN_PROGRESS`, and does not
start further tasks). Map it in the runner: `--on-failure stop` (default) halts the whole run leaving
that task `IN_PROGRESS`; `--on-failure skip` advances. Independent tasks that already completed in the
layer stay committed. Preserve the existing return-code taxonomy semantics (BLOCKED_BY_DEP,
ENVIRONMENT_NOT_CAPABLE, USER_INPUT_REQUIRED, ALL_TASKS_DONE) but interpreted per-layer.
**DoD:** with a seeded failing task among independents, `--on-failure stop` halts and leaves exactly the
failing task `IN_PROGRESS` while the independents that finished remain COMPLETE; HANDOFF.md records it.

### T5 - Loop termination: progress vs all-done vs blocked `TASK:PENDING`
Depends on T2, T3.
Ensure the main loop terminates correctly under the layer model: continue while the layer makes

**DoD:** a plan whose remaining tasks are all dependency-blocked exits 0 cleanly (not a failure); a
fully-completable plan reaches all-done; neither spins past a no-progress layer.
